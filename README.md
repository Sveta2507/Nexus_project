# Nexus

Nexus — браузерна багатопотокова розподілена інформаційна система для захищеної дистанційної комунікації групи до 10 учасників. Система поєднує текстовий чат, загальний і приватні канали, наскрізне шифрування повідомлень приватних каналів, адресну демонстрацію документів і презентацій, синхронізацію сторінки та курсора, потокове голосове мовлення і міжвузлову реплікацію даних.

Серверна частина реалізована мовою Python. Клієнт працює у браузері та не потребує окремого встановлення. Docker, Node.js, Redis і зовнішній сервер бази даних не використовуються.

## Основні можливості

- реєстрація, автентифікація та відображення присутності користувачів;
- загальний відкритий канал і приватні канали з визначеним складом учасників;
- E2EE для текстових повідомлень приватних зашифрованих каналів;
- обмін повідомленнями в реальному часі через WebSocket;
- збереження історії чатів окремо для кожного каналу;
- реплікація користувачів, каналів, ключів, повідомлень і документів між незалежними вузлами;
- автоматична початкова реплікація історії під час підключення нового порожнього вузла;
- дворівневий outbox: IndexedDB у браузері до прийняття повідомлення сервером і персистентна SQLite-черга для міжвузлової доставки;
- стани `очікує`, `надіслано`, `доставлено`, `прочитано` з окремими квитанціями для кожного пристрою;
- демонстрація TXT, Markdown, PDF і зображень вибраним адресатам;
- синхронізація сторінки, вертикального й горизонтального прокручування, zoom 50–200% та координат курсора;
- потокове передавання голосу вибраним користувачам;
- діагностика процесу, потоків, WebSocket-з'єднань, годинника Лампорта та черги outbox;
- довідка гарячих клавіш і клавіатурна навігація основними вікнами;
- Swagger UI і OpenAPI-схема для інтеграції з іншим програмним забезпеченням;
- адаптивний вебінтерфейс для комп'ютерів, планшетів і телефонів.

## Архітектура

Кожен вузол Nexus є самостійним Python-сервером FastAPI/Uvicorn із власною базою SQLite. Вузли обмінюються розподіленими подіями та можуть продовжувати локальну роботу при тимчасовій недоступності сусіднього вузла.

Система складається з п'яти основних компонентів:

- браузерний клієнт на HTML, CSS і JavaScript без окремої системи збірки: REST використовується для авторизації, історії та файлів, а WebSocket — для подій реального часу;
- Python-вузол на FastAPI та Uvicorn, який обслуговує власних клієнтів і керує локальними даними;
- окрема SQLite-база кожного вузла;
- сервіс федерації, який передає сусіднім вузлам HMAC-підписані HTTP-події;
- фоновий outbox worker, який відповідає за повторну доставку персистентних подій.

Багатопотоковість і конкурентність реалізовано на двох рівнях:

- асинхронний цикл `asyncio` обслуговує HTTP і WebSocket-з'єднання;
- блокувальні операції SQLite, PBKDF2 та обробки файлів виконуються у `ThreadPoolExecutor` з іменованими системними потоками `nexus-worker_*`;
- спільні лічильники й логічний годинник захищаються `threading.Lock`, а реєстр WebSocket-з'єднань — `asyncio.Lock`;
- SQLite працює у WAL-режимі для безпечного конкурентного читання та запису.

Таке поєднання дає два рівні конкурентності: велика кількість коротких неблокувальних мережевих операцій виконується асинхронно, а обмежений пул реальних системних потоків паралельно виконує блокувальну роботу без зупинки циклу обробки з'єднань.

Доставка має два рівні. Браузер до відправлення створює UUID і час повідомлення, зберігає підготовлений WebSocket-пакет у IndexedDB та одразу показує його зі станом `очікує`. Для приватного каналу локальна черга містить шифротекст і nonce, а не відкритий текст. Після WebSocket-підтвердження запис видаляється; повторна відправка того самого UUID повертає підтвердження без створення дубліката.

Кожна розподілена зміна утворює подію з UUID, ідентифікатором вузла, часом і значенням логічного годинника Лампорта. Події `message`, `message_receipt`, `document`, `user_upsert`, `channel`, `device_key` і `channel_key` записуються в окрему SQLite outbox-чергу для кожного peer-вузла. Фоновий worker повторює доставку з експоненційною затримкою та видаляє запис після успішного прийняття. На вузлі-одержувачі UUID записується до `processed_events`, а `INSERT OR IGNORE` забезпечує ідемпотентне застосування. Повідомлення впорядковуються за парою `(lamport, created_at)`, а після прийняття віддаленої події годинник оновлюється за правилом `max(local_clock, remote_clock) + 1`. Аудіо, рух курсора та інші ефемерні події передаються напряму для мінімальної затримки.

Новий порожній вузол автоматично надсилає HMAC-підписаний запит усім налаштованим peer-вузлам, перевіряє підписи відповідей і обирає найбільш повний доступний початковий знімок. Однією SQLite-транзакцією імпортуються користувачі, канали й учасники, публічні ключі пристроїв, конверти E2EE-ключів, повідомлення, квитанції, документи та UUID уже оброблених подій. Сесії та outbox залишаються локальними для кожного вузла. Після bootstrap вузол переходить до звичайної подієвої реплікації.

Після отримання повідомлення браузер адресата надсилає квитанцію `delivered`, а після відкриття відповідного каналу у видимій вкладці — `read`. Сервер перевіряє належність `device_id` користувачу, зберігає найраніший час доставки й прочитання у `message_receipts` та надійно реплікує квитанцію між вузлами. Власні повідомлення показують кількість пристроїв; наведення на статус показує користувачів, які отримали або прочитали повідомлення. Квитанція містить лише службові ідентифікатори й не розкриває E2EE-текст.

Присутність користувачів оновлюється кожні 10 секунд і має 30-секундний lease. Завдяки цьому після завершення процесу вузла пов'язані з ним користувачі автоматично переходять у стан офлайн.

## Системні вимоги

- Python 3.11 або новіший;
- сучасний браузер із підтримкою WebSocket, Web Crypto API, IndexedDB і Web Audio API;
- Windows PowerShell для наведених команд запуску;
- мережевий доступ до вибраних портів для демонстрації з інших пристроїв;
- HTTPS або `localhost` для доступу браузера до мікрофона.

Python-залежності перелічено у файлі `requirements.txt`. Установлення інших мов програмування не потрібне.

## Автоматичний запуск у Windows

Найпростіший запуск виконується файлом:

```text
START_NEXUS.cmd
```

За відсутності каталогу `.venv` сценарій автоматично:

1. створює локальне віртуальне середовище Python;
2. встановлює залежності з `requirements.txt`;
3. запускає два взаємопов'язані вузли Nexus.

Якщо `.venv` уже існує, повторне встановлення залежностей не виконується. Після зміни `requirements.txt` залежності оновлюються окремою командою:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Завершення обох вузлів виконується комбінацією `Ctrl+C` у вікні запуску.

## Ручне встановлення та демонстраційний запуск

Команди виконуються з каталогу `Nexus`:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python run_demo.py
```

`run_demo.py` запускає два незалежні процеси:

| Вузол | Адреса | База даних | Peer |
|---|---|---|---|
| `node-a` | <http://localhost:8001> | `data/node-a.db` | `http://127.0.0.1:8002` |
| `node-b` | <http://localhost:8002> | `data/node-b.db` | `http://127.0.0.1:8001` |

Дані між вузлами синхронізуються асинхронно. Обліковий запис, створений на одному вузлі, після реплікації стає доступним для входу на іншому вузлі.

Бази даних не видаляються після завершення процесів. Повторний запуск використовує збережені облікові записи, канали, повідомлення, документи та outbox. Зміни схеми для старих баз застосовуються автоматично під час запуску.

Якщо після зміни Wi-Fi або IP-адреси вузол запускається з оновленим `--peer`, pending-події автоматично переносяться зі старої адреси outbox на поточні peer-адреси. Лічильник невдалих спроб скидається, і доставка відновлюється одразу після появи доступного peer-вузла. Якщо `--peer` не задано, старі pending-записи зберігаються без змін і не видаляються.

## Запуск одного вузла

Окремий вузол без федерації запускається так:

```powershell
python run_node.py --node-id node-a --host 0.0.0.0 --port 8001
```

Ручний запуск двох федеративних вузлів виконується у двох окремих терміналах:

```powershell
python run_node.py --node-id node-a --host 0.0.0.0 --port 8001 --peer http://127.0.0.1:8002 --secret "REPLACE-WITH-A-LONG-RANDOM-SECRET"
```

```powershell
python run_node.py --node-id node-b --host 0.0.0.0 --port 8002 --peer http://127.0.0.1:8001 --secret "REPLACE-WITH-A-LONG-RANDOM-SECRET"
```

Значення `--secret` на всіх взаємопов'язаних вузлах має збігатися. Стандартний секрет призначений тільки для локальної навчальної демонстрації.

### Параметри `run_node.py`

| Параметр | Призначення | Типове значення |
|---|---|---|
| `--node-id` | Унікальне ім'я вузла | `node-a` |
| `--host` | Мережева адреса прослуховування | `0.0.0.0` |
| `--port` | HTTP/HTTPS-порт | `8001` |
| `--database` | Шлях до SQLite-бази | `data/<node-id>.db` |
| `--peer` | URL сусіднього вузла; параметр може повторюватися | порожній список |
| `--secret` | Спільний HMAC-секрет федерації | локальний демонстраційний секрет |
| `--ssl-keyfile` | Шлях до приватного ключа TLS | не задано |
| `--ssl-certfile` | Шлях до сертифіката TLS | не задано |

Кожному вузлу призначаються окремі `node-id`, порт і файл бази даних.

Файл SQLite для нового `node-id` створюється автоматично. Якщо він не містить користувацьких даних, вузол фоново запитує початковий знімок у доступних `--peer`. Для подальшого двостороннього обміну новий вузол також потрібно додати до списків `--peer` на наявних вузлах.

## Доступ із локальної мережі

Прив'язка до `0.0.0.0` робить вузол доступним через мережеві інтерфейси комп'ютера. Адреса для іншого пристрою має вигляд:

```text
http://IP-АДРЕСА-КОМП'ЮТЕРА:8001
```

У Windows Firewall доступ для Python доцільно дозволяти тільки для приватних мереж. Порт має бути вільним і доступним між пристроями. Для перевірки звичайного чату HTTP достатньо, але мікрофон на віддаленому пристрої потребує HTTPS.

Для двох вузлів на одному ноутбуці peer-адресами мають бути `http://127.0.0.1:8001` і `http://127.0.0.1:8002`; такі адреси не залежать від Wi-Fi. Для двох фізичних ноутбуків після переходу в іншу мережу вказуються їхні нові IP-адреси або стабільні мережеві імена. До відновлення маршруту дані зберігаються в outbox, а після запуску з актуальним `--peer` доставка поновлюється автоматично.

## HTTPS і мікрофон

Доступ до `getUserMedia()` дозволяється браузером на `localhost` або у захищеному HTTPS-контексті. Локальний самопідписаний сертифікат створюється так:

```powershell
python create_certificate.py
```

Запуск HTTPS-вузла:

```powershell
python run_node.py --node-id node-a --host 0.0.0.0 --port 8443 --ssl-keyfile certs/key.pem --ssl-certfile certs/cert.pem
```

Після запуску використовується адреса:

```text
https://IP-АДРЕСА-КОМП'ЮТЕРА:8443
```

Самопідписаний сертифікат придатний для навчальної локальної демонстрації. На клієнтському пристрої сертифікат має бути підтверджений або доданий до довірених. Для публічного доступу потрібен сертифікат від довіреного центру сертифікації або HTTPS-термінація на захищеному reverse proxy чи tunneling-сервісі.

## Port forwarding і доступ через Інтернет

Для демонстрації через port forwarding зовнішній TCP-порт перенаправляється на порт вузла Nexus, який прослуховує `0.0.0.0`. Публічне розгортання потребує таких умов:

- використання HTTPS із чинним сертифікатом;
- заміна стандартного federation secret на довге випадкове значення;
- однаковий секрет на всіх peer-вузлах;
- використання досяжних peer-адрес у параметрах `--peer`;
- фільтрація доступу правилами брандмауера;
- відсутність прямої публікації непотрібних портів;
- перевірка дозволів браузера на мікрофон і WebSocket-з'єднання.

Port forwarding не змінює логіку застосунку: браузер підключається до опублікованої HTTPS-адреси, а вузли продовжують обмінюватися підписаними федеративними подіями.

## Канали та E2EE

Загальний канал `lobby` доступний усім автентифікованим користувачам і навмисно не використовує наскрізне шифрування. Приватний канал містить явний список учасників. Доступ до каналу перевіряється для REST-запитів, WebSocket-подій і міжвузлової доставки.

Історія чату групується за локальними календарними днями з видимими розділювачами `Сьогодні`, `Вчора` або повною датою. Кожна часова мітка містить ISO `datetime` і повний локалізований опис для екранних дикторів. Повідомлення, доставлені із затримкою через outbox, автоматично займають правильну хронологічну позицію за часом їх створення, а не додаються після новіших повідомлень.

Для E2EE використовуються такі механізми:

1. Для кожної пари «обліковий запис + браузерний профіль» створюється окрема пара ключів ECDH P-256.
2. Приватний ECDH-ключ зберігається в IndexedDB як неекспортований `CryptoKey`.
3. Для каналу генерується випадковий 256-бітний ключ AES-GCM.
4. Ключ каналу окремо загортається для кожного пристрою учасника за допомогою ECDH, HKDF-SHA256 та AES-GCM.
5. Кожне повідомлення шифрується AES-256-GCM із новим 96-бітним nonce.
6. Ідентифікатор каналу додається як authenticated additional data.
7. Розшифрування виконується тільки у браузері учасника.

Для створення зашифрованого каналу кожен майбутній учасник один раз входить до застосунку, після чого реєструється публічний ключ його пристрою. Новий пристрій публікує власний відкритий ключ і формує запит конверта, а один із раніше авторизованих пристроїв учасників повторно загортає для нього ключ каналу.

Якщо в одному профілі браузера почергово входять різні користувачі, їхні `device_id` та ECDH-ключі зберігаються окремо. Це не дозволяє новому користувачу успадкувати криптографічну ідентичність попереднього облікового запису.

Сервер зберігає шифротекст, nonce, публічні ключі, зашифровані конверти та службові метадані: автора, канал, учасників і час. Відкритий текст E2EE-повідомлення до бази не записується.

Таким чином, E2EE захищає текст приватних каналів від читання зі сховища сервера: шифрування й розшифрування виконуються на кінцевих пристроях, а сервер маршрутизує та реплікує лише шифротекст. Відбиток власного публічного ключа пристрою відображається у вікні стану системи.

## Документи, презентації та аудіо

Підтримуються файли до 8 МБ із такими MIME-типами:

- TXT і Markdown;
- PDF;
- PNG і JPEG;
- WebP і GIF.

Кожний документ належить конкретному каналу. Сервер перевіряє членство під час отримання списку, завантаження файла, читання вмісту та запуску демонстрації. У приватному каналі документ бачать тільки його учасники; документи загального каналу доступні всім авторизованим користувачам. Старі документи, створені до появи цього правила, автоматично переносяться до загального каналу під час оновлення схеми БД.

Демонстрація документа адресно передається вибраним учасникам поточного каналу. Кожна WebSocket-подія містить UUID документа, ідентифікатор сесії, послідовний номер, дію `start`, `update` або `stop`, номер сторінки, нормалізоване вертикальне й горизонтальне прокручування, масштаб, координати курсора та список адресатів. Послідовний номер відсіює застарілі оновлення, а демонстратор є авторитетним джерелом спільного стану.

Прозорий інтерактивний шар охоплює всю область матеріалу, включно з PDF-iframe, і стабільно фіксує рух курсора. Кнопки `−`, `100%`, `+` і комбінації `Ctrl+−`, `Ctrl++`, `Ctrl+0` змінюють zoom від 50% до 200% для TXT/Markdown, PDF і зображень; глядач отримує той самий стан. Колесо миші прокручує збільшений матеріал, а на межі PDF перемикає сторінку. PDF-iframe створюється повторно лише при фактичній зміні сторінки, тому часті оновлення не спричиняють мерехтіння. У глядацькому режимі локальне керування сторінками, zoom і вбудованим PDF-переглядачем заблоковане.

Курсор використовує геометрію відповідного формату: область перегляду для PDF, фактичний прямокутник для зображення та семантичну позицію символу для TXT/Markdown. Після прокручування текстова позиція повторно визначається під нерухомою мишею, тому вказівник не отримує «ефекту скролу». Це зберігає точність за різної роздільної здатності та перенесення рядків. Після команди завершення глядацьке вікно закривається одразу; при аварійній втраті демонстратора — автоматично після семисекундного тайм-ауту.

Голос захоплюється Web Audio API монофонічними блоками по 2048 семплів. Кожен семпл перетворюється з `Float32` на little-endian `PCM Int16`, блок кодується у Base64 і передається через WebSocket визначеним адресатам. Одержувач декодує фрагмент у `AudioBuffer` та планує його відтворення одразу після попереднього блока конкретного відправника. Повний аудіозапис не накопичується, тому голос звучить у міру надходження даних.

## Демонстраційний сценарій

1. Запускається `python run_demo.py` або `START_NEXUS.cmd`.
2. У першому браузерному профілі завантажується `http://localhost:8001` і реєструється користувач `alice`.
3. У другому профілі завантажується `http://localhost:8002` і реєструється користувач `bob`.
4. Після реплікації обидва користувачі відображаються на обох вузлах.
5. Через кнопку `+` створюється приватний E2EE-канал з обома учасниками.
6. Зашифроване повідомлення надсилається з одного вузла та розшифровується у браузері на іншому.
7. Біля повідомлення Alice статус послідовно змінюється з `надіслано` на `доставлено`, а після відкриття каналу Bob — на `прочитано`.
8. Для демонстрації документа вибирається адресат, завантажується підтримуваний файл і вмикається трансляція.
9. Зміна сторінки, scroll, zoom і рух курсора відображаються у вибраного адресата.
10. Після надання браузеру дозволу кнопка мікрофона біля кнопки надсилання запускає та зупиняє потокове мовлення вибраним учасникам.
11. У вікні «Стан системи» відображаються PID, потоки, вузол, база, годинник Лампорта, outbox і метрики.
12. Для демонстрації відмовостійкості один вузол зупиняється, на іншому створюється персистентна подія, після чого вузол відновлюється. Подія доставляється з outbox без дублювання.

## API

Повністю локальна інтерактивна документація доступна за шляхом `/docs`, OpenAPI JSON — `/openapi.json`. Сторінка `/docs` не використовує зовнішні CDN і працює без доступу до інтернету.

| Метод | Маршрут | Призначення |
|---|---|---|
| POST | `/api/auth/register` | Реєстрація користувача |
| POST | `/api/auth/login` | Створення сесії |
| POST | `/api/auth/logout` | Завершення поточної сесії |
| GET | `/api/me` | Дані поточного користувача і вузла |
| GET | `/api/users` | Користувачі та їхня присутність |
| GET/POST | `/api/channels` | Отримання і створення каналів |
| GET/POST | `/api/keys/devices` | Публічні ключі браузерних пристроїв |
| GET | `/api/channels/{id}/key` | Конверт ключа каналу для пристрою |
| POST | `/api/channels/{id}/keys` | Публікація конвертів ключа каналу |
| GET/POST | `/api/messages` | Історія і надсилання повідомлень |
| GET/POST | `/api/documents` | Бібліотека і завантаження документів |
| GET | `/api/documents/{id}/content` | Вміст документа |
| GET | `/api/health` | Перевірка доступності вузла |
| GET | `/api/system` | Діагностика вузла, потоків, БД і метрик |
| WS | `/ws` | Чат, ключові запити, презентація й аудіо |
| POST | `/api/federation/events` | HMAC-захищена міжвузлова реплікація |
| POST | `/api/federation/snapshot` | HMAC-захищений початковий знімок для нового вузла |

Захищені REST-маршрути використовують заголовок `Authorization: Bearer TOKEN`.

## Перевірка

Модульні тести:

```powershell
python -m unittest discover -s tests -p "test_*.py" -v
```

Повна інтеграційна перевірка:

```powershell
python tests/integration_check.py
```

Інтеграційний сценарій автоматично запускає тимчасові вузли та перевіряє:

- заголовки безпеки, реєстрацію й автентифікацію;
- HMAC-підпис і федеративну реплікацію;
- автоматичну початкову реплікацію історії на новий третій вузол;
- відновлення доставки з outbox;
- міжвузлові квитанції доставки та прочитання для окремих пристроїв;
- приватні E2EE-канали та заборону доступу стороннього користувача;
- відсутність відкритого тексту зашифрованого повідомлення у серверній БД;
- документи, презентацію й адресну передачу аудіо;
- 10 одночасних WebSocket-користувачів.

Перевірка E2EE між двома справжніми браузерами розміщена у `tests/e2ee_two_browser_check.py`. Для неї окремо запускаються два вузли та два екземпляри Edge/Chrome з різними профілями й увімкненим remote debugging. Тест перевіряє ECDH-узгодження, загортання ключа, AES-256-GCM, міжвузлову доставку, браузерне розшифрування, offline outbox і перехід статусу до `прочитано`.

Перевірка встановлених залежностей:

```powershell
python -m pip check
```

## Безпека

- Паролі хешуються PBKDF2-HMAC-SHA256 із випадковою 128-бітною сіллю та 390 000 ітерацій.
- Сесійний токен створюється криптографічно стійким генератором випадкових чисел, а в базі зберігається лише його SHA-256-відбиток.
- Федеративні події захищаються HMAC-SHA256 над часовою міткою і точним тілом запиту; допустиме відхилення часу становить 90 секунд для протидії повторному відтворенню запитів.
- Content Security Policy та додаткові HTTP-заголовки зменшують ризик виконання стороннього коду.
- Текст повідомлень вставляється в DOM через `textContent`, тому HTML-код із повідомлення не виконується.
- WebSocket-токен передається через субпротокол, а не через URL чи журнали доступу.
- HTTPS захищає транспортний канал для браузерних і міжвузлових з'єднань та надає безпечний контекст для мікрофона.
